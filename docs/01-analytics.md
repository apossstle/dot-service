## 2. SWOT-анализ

**Сильные стороны (Strengths)**
- Готовая база за прошлый семестр, не начинаем с нуля.
- Корректная обработка граничных случаев (вершины, рёбра, отверстия) — подтверждена тестами.
- Веб-интерфейс с реальной картой — проект демонстрируется без дополнительной подготовки.
- Multi-user изоляция через cookie — полигоны одного пользователя не видны другому.
- Отсутствие внешних зависимостей на старте — чистая стандартная библиотека Python.

**Слабые стороны (Weaknesses)**
- Хранилище in-memory — данные теряются при рестарте.
- Единственный пространственный индекс (GridIndex) плохо работает при неравномерном распределении полигонов.
- Нет булевых операций над полигонами (объединение, пересечение).
- HTTP-слой на базовом `http.server` — ограниченная валидация, нет OpenAPI-документации.
- Нет механизмов пакетного импорта данных.

**Возможности (Opportunities)**
- Применимо в сервисах геозонирования (доставка, такси, страхование).
- Открытые источники геоданных (OpenStreetMap Overpass) позволяют быстро получить реальные тестовые наборы.
- Экосистема Python богата готовыми библиотеками (shapely, rtree, geoalchemy2) — не надо изобретать велосипед на вычислительных задачах.

**Угрозы (Threats)**
- Сжатые сроки (12 недель) при шести крупных задачах.
- Риск разъехаться по приоритетам внутри команды.
- Возможные сложности с установкой PostGIS на Windows у аналитика.
- Проблемы с производительностью/памятью при работе с реальными крупными геоданными (десятки тысяч полигонов).

## 4. Обоснование выбора технологий

**Пространственный индекс: `rtree` (библиотека Python)**
Альтернативы: написать с нуля, использовать KD-Tree, использовать Quadtree. Выбор `rtree` обусловлен: (1) обёртка над проверенной C-библиотекой libspatialindex; (2) R-Tree лучше работает с реальными географическими полигонами, у которых bounding box'ы сильно различаются по размеру; (3) собственная реализация увеличит трудозатраты без выигрыша в учебной ценности для проекта такого объёма.

**Топологические операции: `shapely`**
Альтернативы: написать с нуля (Weiler-Atherton, Vatti), использовать `pyclipr`. Выбор `shapely` обусловлен: (1) обёртка над GEOS — стандарт де-факто в геоинформатике; (2) корректная обработка вырожденных случаев; (3) полная совместимость с PostGIS, что упрощает интеграцию.

**СУБД: PostgreSQL + PostGIS**
Альтернативы: SQLite + SpatiaLite, MongoDB с геоиндексами. Выбор PostGIS обусловлен: (1) индустриальный стандарт для геоданных; (2) родной тип `geometry` снимает необходимость собственной сериализации; (3) поддержка SQL-операций над геометриями на уровне СУБД (отложенная оптимизация в будущем); (4) PostgreSQL — тема, встречающаяся во многих дисциплинах образовательной программы, навык переносим.

**HTTP-фреймворк: FastAPI (миграция с `http.server`)**
Альтернативы: Flask, Django, остаться на `http.server`. Выбор FastAPI обусловлен: (1) автоматическая генерация OpenAPI/Swagger-документации — закрывает требование диплома; (2) валидация запросов через pydantic заменяет ручные проверки в хендлерах; (3) асинхронность в перспективе ускорит пакетные запросы.

**Карта: Leaflet + OpenStreetMap**
Уже используется с прошлого семестра. Альтернативы (Mapbox, Google Maps) требуют платных API-ключей, что противоречит ключевому принципу продукта — независимости от облачных вендоров.

## 5. User stories

**US-1. Проверка попадания адреса в зону доставки**
Как логистический оператор, я хочу загрузить полигон зоны доставки и быстро проверять координаты заказов на попадание в неё, чтобы автоматически маршрутизировать заявки.
*Acceptance:* полигон можно создать через REST-эндпоинт `POST /polygons`; запрос `POST /query/point-in-polygon` возвращает список попадающих полигонов за <100 мс при 10 000 полигонов в хранилище; корректно обрабатываются точки на границе.

**US-2. Расчёт пересечения охранных и строительных зон**
Как сотрудник ГИС-отдела градостроительной организации, я хочу вычислять пересечение полигонов охранных зон и предполагаемого строительства, чтобы заранее выявлять потенциальные конфликты.
*Acceptance:* эндпоинт `POST /operations/intersection` принимает два polygon_id, возвращает результат в GeoJSON и WKT; если пересечение пустое — возвращает `null` с кодом 200, а не ошибку; результат отрисовывается на карте отдельным слоем.

**US-3. Поиск полигонов, покрывающих точку интереса**
Как аналитик рекламной платформы, я хочу по координатам точки получить все рекламные геозоны, которые её содержат, чтобы определить применимые таргетинги.
*Acceptance:* в ответе на `POST /query/point-in-polygon` возвращаются все перекрывающиеся полигоны, а не только первый найденный; каждый полигон содержит свои `properties` (например, идентификатор рекламной кампании).

**US-4. Пакетная загрузка кадастровых участков**
Как разработчик геоинформационного приложения, я хочу загрузить несколько тысяч полигонов из GeoJSON-файла одной командой, чтобы не вызывать API по одной записи.
*Acceptance:* эндпоинт `POST /import` принимает FeatureCollection из 10 000 полигонов за время не дольше 30 с; возвращает отчёт с числом успешно загруженных и списком ошибок с указанием индексов проблемных записей.

**US-5. Визуальная проверка результата топологической операции**
Как студент, изучающий вычислительную геометрию, я хочу видеть результат объединения или пересечения полигонов на карте, чтобы наглядно понимать работу алгоритмов.
*Acceptance:* вкладка «Операции» в веб-интерфейсе позволяет выбрать 2+ полигонов на карте, выбрать операцию (union/intersection/difference/buffer); результат отрисовывается отличающимся цветом поверх исходных полигонов.

**US-6. Загрузка полигонов из внешнего источника OSM**
Как исследователь городской инфраструктуры, я хочу подтянуть границы всех парков района из OpenStreetMap одной командой, чтобы не искать и не рисовать их вручную.
*Acceptance:* эндпоинт `POST /import?format=overpass` принимает Overpass QL-запрос, возвращает число загруженных объектов; результат виден на карте без перезагрузки страницы; при ошибке Overpass API возвращается осмысленная 502-ошибка.

**US-7. Переключение между хранилищами без потери работоспособности**
Как разработчик проекта, я хочу переключать режим хранилища (in-memory / PostgreSQL) переменной окружения, чтобы запускать быстрые локальные тесты и промышленный режим без правки кода.
*Acceptance:* `STORAGE=memory python main.py` и `STORAGE=postgres python main.py` поднимают сервис одинаково; тесты проходят в обоих режимах; переключение не требует миграций вручную.

**US-8. Сравнение производительности разных индексов**
Как инженер, оптимизирующий сервис под свои данные, я хочу сравнить производительность GridIndex и R-Tree на моих типичных нагрузках, чтобы выбрать правильный индекс.
*Acceptance:* скрипт `benchmarks/bench_index.py` принимает путь к набору полигонов и число запросов, выводит сравнительную таблицу по времени построения, времени запроса и памяти для обоих индексов.

**US-9. Изоляция данных между пользователями**
Как пользователь веб-интерфейса, я хочу работать со своим набором полигонов, не видя чужих, чтобы случайно не удалить или не изменить чужие объекты.
*Acceptance:* полигоны одного пользователя (определяемого по cookie `ps_uid`) не отображаются в ответах API другому пользователю; `GET /polygons`, `GET /stats` и `POST /query/point-in-polygon` возвращают только свои записи.

**US-10. Развёртывание сервиса одной командой**
Как DevOps-инженер, разворачивающий сервис в новой среде, я хочу поднять весь стек (сервис + СУБД) одной командой, чтобы не настраивать окружение вручную.
*Acceptance:* `docker compose up` поднимает сервис и PostgreSQL с PostGIS; данные сохраняются между перезапусками через volume; сервис доступен на `http://localhost:8080` без дополнительной настройки.

## 6. Нефункциональные требования

| Категория | Требование |
|---|---|
| Производительность PIP | Проверка одной точки против 10 000 полигонов — не дольше 100 мс. |
| Производительность топологии | Пересечение двух полигонов по 1000 вершин — не дольше 500 мс. |
| Пакетный импорт | Загрузка 10 000 полигонов из GeoJSON-файла — не дольше 30 с. |
| Использование памяти | Для 10 000 полигонов средней сложности — не более 500 МБ RSS процесса. |
| Совместимость | Работа на Windows, Linux, macOS. Python 3.10+. |
| Развёртывание | Запуск через `docker compose up` без ручной настройки. |
| Документация | OpenAPI-спецификация доступна по `/docs`, README с примерами на двух ОС. |
| Тестирование | Покрытие автотестами ≥90% строк, не менее 150 тестов. |

## 7. Анализ аналогов

На рынке присутствуют инструменты, которые частично закрывают задачу работы с полигонами, но ни один не является прямым аналогом — каждый решает узкую часть, оставляя остальное на разработчика.

**PostGIS** — расширение СУБД PostgreSQL, лицензия GPLv2, бесплатно. Предоставляет полный набор геометрических функций (PIP, топологические операции, индексы) через SQL, но не является сервисом: нет REST API, нет веб-интерфейса, нет готового приложения. Требует знаний SQL и администрирования PostgreSQL. Целевая аудитория — опытные разработчики и DBA.

**Shapely** — Python-библиотека, обёртка над C-библиотекой GEOS. Лицензия BSD, бесплатно. Предоставляет только вычислительное ядро — типы геометрий и операции над ними в рамках одного процесса. Нет хранилища, сервисного слоя, интерфейса. Подходит для скриптов обработки геоданных и аналитики, но не для эксплуатации как сервис.

**Azure Maps Spatial** — облачный API от Microsoft. Оплата по факту использования, около 5 USD за 1000 транзакций (тариф S1). С сентября 2025 года официально снят с поддержки (retiring), новые интеграции невозможны. Требует подписки Azure и привязки к экосистеме Microsoft.

**Turf.js** — JavaScript-библиотека для геометрических вычислений в браузере и Node.js. Лицензия MIT, бесплатно. Клиентская, без серверной части и хранилища, требует Node.js как рантайм. Подходит для фронтенд-визуализации, не заменяет бэкенд-сервис.

**QGIS** — свободное десктопное ГИС-приложение, GPLv2. Полноценное картографическое рабочее место с богатыми возможностями анализа и визуализации, но именно приложение, а не встраиваемый сервис или API. Целевая аудитория — геодезисты, картографы, ГИС-специалисты. Для интеграции в собственный продукт непригоден.

**Облачные картографические API (Yandex Maps, Google Maps Platform)** — ориентированы прежде всего на геокодирование, роутинг и отображение карт. Работа с произвольными пользовательскими полигонами не является первоклассным сценарием; тарификация основана на количестве запросов и требует привязки к платёжному аккаунту.

**Итог:** среди перечисленных решений нет инструмента, который объединял бы одновременно REST API, готовый веб-интерфейс, встраиваемую библиотеку и локальное развёртывание без обязательной привязки к тяжёлой СУБД или облачному провайдеру. Разрабатываемый продукт занимает эту нишу.
