# Бенчмарки пространственных индексов (предварительно)

**Дата прогона:** 25 октября 2026
**Что сравниваем:** `GridIndex` и `RTreeIndex` — только этап отбора кандидатов по bounding box, без точной проверки point-in-polygon.
**Окружение:** macOS, Python 3.14, rtree 1.x, один поток.

Сырые данные — `benchmarks/results/*.csv`.

## Как воспроизвести

```bash
python benchmarks/bench_index.py -n 10000 -q 10000 --out benchmarks/results/synth_n10000.csv
python benchmarks/fetch_moscow.py
python benchmarks/bench_moscow.py --cell-size 0.05 --out benchmarks/results/moscow_cell0.05.csv
```

Если `fetch_moscow.py` падает с `CERTIFICATE_VERIFY_FAILED` на macOS — запустить `Install Certificates.command` из папки Python в Applications, либо скачать ответ Overpass через curl и передать его в `--input`.

## Наборы данных

| Набор | Полигонов | Описание |
|---|---|---|
| synth_n100 / n1000 / n10000 | 100 / 1 000 / 10 000 | прямоугольники со стороной 1–20 в области 1000×1000, равномерно |

## Выводы

1. **На запросах GridIndex быстрее R-Tree в 3–38 раз.** У сетки запрос — это поиск ячейки в словаре, O(1). У `rtree` каждый вызов проходит через ctypes в libspatialindex, и эти накладные расходы (~4.5 мкс) больше, чем сам поиск на таких объёмах.
2. **R-Tree не зависит от настройки.** У сетки всё решает `cell_size`: на крупных перекрывающихся полигонах с маленькой ячейкой построение заняло 5.2 с и ~1.7 ГБ памяти против 0.13 с и ~3 МБ у R-Tree. Если подобрать ячейку неудачно, сетка деградирует на порядки; R-Tree ведёт себя одинаково.
3. **На крупных полигонах R-Tree экономнее по памяти** примерно в 10 раз: сетка хранит id полигона в каждой ячейке, которую он покрывает.
4. **На районах Москвы оба индекса укладываются в микросекунды**, требование «одна точка против 10 000 полигонов до 100 мс» с запасом выполняется любым из них.

**Предварительная рекомендация:** по умолчанию оставить `GridIndex` для небольших равномерных данных, а `RTreeIndex` включать для реальных данных с полигонами разного размера, где `cell_size` заранее не подобрать.

## Ограничения замера

- Память — это разница RSS процесса до и после построения. Она шумная, особенно на маленьких наборах (отсюда «~0» у Москвы).
- Меряется только отбор кандидатов. Полный PIP-запрос с точной проверкой геометрии — в итоговом отчёте (задача 6.5).
- Один прогон на конфигурацию, без усреднения. Для финального отчёта нужны повторы и разброс.
